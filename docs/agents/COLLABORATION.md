# AI 협업 운영 규칙

이 레포는 대표 1명과 AI 직원 2명(GPT/Codex, Claude)이 함께 운영합니다.
두 AI는 **작업마다 구현자와 검수자를 번갈아 맡습니다.** 같은 AI가 자기 작업을 스스로 승인하지 않는 것이 핵심 원칙입니다.

## 1. 역할

| 역할 | 담당 | 하는 일 |
|---|---|---|
| 대표 | 사용자 | 업무 지시(Issue), 우선순위 결정, 최종 병합(Merge) |
| 구현자 | GPT 또는 Claude | 명세 확인 → 브랜치에서 구현 → 테스트 추가 → PR 작성 |
| 검수자 | 구현자가 아닌 다른 AI | `AGENTS.md` 기준 리뷰, 위험 지적, 승인/수정 요청 |
| 품질관리 | GitHub Actions + Vercel | CI 검증, PR별 미리보기 배포 |

공통 규칙서는 `AGENTS.md`입니다. 두 AI 모두 이 문서를 최우선 기준으로 따릅니다.

## 2. 담당 배정 (라벨)

대표가 이슈를 만들 때 라벨 하나로 구현자를 지정합니다. 검수자는 자동으로 반대편입니다.

| 라벨 | 구현 | 검수 |
|---|---|---|
| `impl:gpt` | GPT | Claude |
| `impl:claude` | Claude | GPT |

대표가 지정하지 않으면 아래 기본값을 씁니다. 목적은 **서로 다른 시각으로 한 번 더 걸러내는 것**이므로, 한쪽에 몰리지 않게 섞습니다.

- 적재 엔진·안전 제약(`src/engine`, 지지/적층/하중/관성) → 직전 엔진 작업의 반대편이 구현
- UI·3D 화면·모바일 → `impl:gpt`
- 설계 문서, 명세 작성, 테스트 보강, 리팩터링 → `impl:claude`
- 버그 수정 → 해당 코드를 마지막으로 만든 AI가 **아닌** 쪽이 구현

## 3. 업무 흐름

```
대표: Issue 작성 (업무지시서 양식 + impl 라벨)
  ↓
구현자: 이슈에 작업 계획 코멘트 (AGENTS.md 13절 1~2단계)
  ↓
구현자: 브랜치 생성 → 구현 → 테스트 → PR (PR 양식 체크리스트 작성)
  ↓
CI 자동 검증 + Vercel 미리보기 URL 생성
  ↓
검수자: PR 리뷰 (승인 / 수정 요청)
  ↓  수정 요청 시 구현자가 고치고 다시 검수 (최대 3회, 넘으면 대표에게 판단 요청)
대표: 미리보기 확인 → Merge
```

### 호출 방법
- Claude: 이슈나 PR 코멘트에 `@claude` + 지시 내용
- GPT(Codex): Codex의 GitHub 연동으로 코멘트 호출 (`@codex` 등, OpenAI 설정에 따름)

## 4. 브랜치·커밋 규칙

- 브랜치: `gpt/<이슈번호>-<짧은설명>` 또는 `claude/<이슈번호>-<짧은설명>`
- `main`에 직접 커밋 금지. 모든 변경은 PR로.
- PR 하나 = 이슈 하나 = 일관된 변경 하나 (`AGENTS.md` 13절).
- 커밋 메시지에 이슈 번호 포함: `fix(engine): 누적 상부하중 계산 수정 (#42)`

## 5. 검수자가 반드시 확인할 것

1. 안전 제약(경계·충돌·지지·적층·상부하중·총중량)을 적재율을 위해 완화하지 않았는가
2. 같은 입력에 같은 결과가 나오는가 (결정론, 시간 기반 중단 없음)
3. 변경된 규칙에 회귀 테스트가 있는가
4. `BOX_ONLY` 결과가 팔레트/MIXED 변경 때문에 바뀌지 않았는가
5. UI 로직과 엔진 로직이 섞이지 않았는가
6. 모바일 화면이 깨지지 않았는가 (Vercel 미리보기로 확인)

검수 결과는 PR 리뷰로 남기고, 마지막 줄에 다음 중 하나를 씁니다.
- `판정: 승인` — 대표가 병합해도 됨
- `판정: 수정 요청` — 구현자가 고쳐야 할 항목을 번호로 나열
- `판정: 대표 판단 필요` — 규칙끼리 충돌하거나 사업적 결정이 필요한 경우

## 6. 의견이 갈릴 때

두 AI의 판단이 다르면 억지로 합의하지 않습니다. 검수자가 PR에 **양쪽 주장과 근거, 선택지별 영향**을 정리하고 `판정: 대표 판단 필요`로 넘깁니다. 대표의 결정은 이슈에 기록하고, 반복될 규칙이면 `AGENTS.md`에 반영합니다.

## 7. 기록 원칙

- 작업 보고서는 루트에 새 `.md` 파일로 만들지 않고 **PR 설명**에 씁니다.
- 릴리스 단위 변경은 `CHANGELOG.md`에만 요약합니다.
- 배포는 `main` 병합으로 자동 진행됩니다. 재배포용 트리거 파일은 만들지 않습니다.
