# 기업 작업 공간 · 첫 서비스 기반

결제는 대표의 별도 지시 이후 구현한다. 이 변경은 기업별 협업과 명시적인 출하 계획 공유만 추가하며 개인 저장 데이터 및 적재 엔진은 그대로 유지한다.

## 이용 흐름

PC 시뮬레이터의 메뉴 → 기업 작업 공간에서 기존 회원 계정으로 기업을 생성한다. 현재 적재안을 제목과 함께 저장하면 입력·계산 결과·저장 당시 검사 기록을 기업에 공유한다. 전체 개인 상품/박스 목록이나 브라우저 세션은 공유하지 않는다.

직원의 가입 이메일과 역할을 지정해 7일간 유효한 일회용 초대코드를 발급한다. 메일 자동 발송은 이번에 추가하지 않았으며, 관리자가 초대받은 직원에게 직접 전달한다. 기존 회원 인증은 이메일 소유 확인을 하지 않는 구조이므로 실제 직원의 가입 계정을 관리자가 확인해야 한다. 코드와 로그인 이메일이 모두 일치해야 참여할 수 있다.

계획 담당이 검토를 요청하면 다른 검토 담당이 승인하거나 의견과 함께 수정을 요청한다. 본인이 제출한 계획은 본인이 승인할 수 없다. 저장하면 이전 승인은 해제되고 새 버전의 초안으로 돌아간다. 모든 입력 버전과 활동은 서버에 남는다. 동시에 같은 버전을 수정하면 한 요청만 저장되고 나머지는 버전 충돌로 거절된다.

`/workspace.html`은 PC·휴대폰 조회 페이지다. 웹GL·적재 계산 엔진을 불러오지 않고 기업 계획, 품목별 수량, 배치 좌표와 미적재 사유를 조회한다. PC 메인 화면의 개인 시뮬레이터는 기존 방식으로 계속 이용한다. 공유 목록은 20건씩, 실제 계산 결과는 선택한 계획만 조회한다.

## 역할

|역할|조회|계획 작성·제출|다른 제출자 검토|직원 관리|
|---|---|---|---|---|
|소유자|가능|가능|가능|가능|
|관리자|가능|가능|가능|관리자 이외 역할만|
|계획 담당|가능|가능|불가|불가|
|검토 담당|가능|불가|가능|불가|
|조회 담당|가능|불가|불가|불가|

소유자는 이 화면에서 해제·변경할 수 없다. 초대로 소유자나 관리자 권한을 부여하지 않는다. 직원의 역할 변경·참여 해제 시 그 직원이 기존에 발급한 미사용 초대도 만료된다.

## 안전 및 데이터 경계

업무 검토 승인은 운송 안전 인증이 아니다. `recordedVerification`은 브라우저에서 저장한 과거 검사 기록이며 서버가 물리 검사를 재실행하거나 인증 서명을 한 값이 아니다. WHAT-IF, 수량 불일치, 정적/운영 오류, 검사 미통과·결과 없음은 제출할 수 없다. 품목별 `입력 = 배치 + 미적재`, 알려진 품목 및 중복 unitId를 서버에서도 검사한다.

공유 입력을 시뮬레이터로 불러오면 기존 관성 기록·물리 대상·수동 배치·팔레트 결과를 폐기한다. 공유 결과와 업무 승인으로 현재 PASS를 복원하지 않는다. 다시 계산·검증해야 한다. 박스/팔레트 공유를 지원하며 MIXED 공유는 명시적 안내와 함께 거절한다.

현재 회원은 Supabase Auth JWT가 아닌 자체 opaque session을 쓴다. 기존 Edge Function에서 토큰 해시·만료·회원 상태 확인 후 확정한 회원 ID만 RPC에 전달한다. 회사 RPC와 6개 테이블은 `service_role` 전용이다. RLS를 켜고 `PUBLIC`, `anon`, `authenticated` 접근을 회수한다. 서비스 키는 브라우저에 보내지 않는다. 회사별 역할은 RPC에서 다시 확인한다. 공유 DB의 다른 서비스 테이블·권한은 수정하지 않는다.

## 검증과 운영 반영

- `npm run test -- src/company`: PGlite 실제 SQL 권한·초대·버전·승인, API 입력/actor 경계, 입력 공유·복원 검증
- `npm run test:e2e -- e2e/company-workspace.spec.ts --project=chromium-desktop --project=chromium-mobile --workers=1 --retries=0`: 실제 UI → 회사 API 처리 함수 → PGlite, 합성 회원·토큰만 사용하고 외부 네트워크 차단
- `npm run verify:full -- -- --project=chromium-desktop --workers=1 --retries=0`: 기존 전체 출시 검사

Docker가 실행되지 않아 Supabase 로컬 스택은 실행하지 못했다. SQL은 PGlite PostgreSQL으로 검증했다. 단일 연결이므로 실제 복수 DB 세션의 잠금 경쟁, 운영 세션 인증과 운영 RLS/Edge 설정 검증을 대체하지 않는다.

운영 적용 시 대표의 배포 지시 후 새 마이그레이션 `20261009103147_loading_company_service.sql`만 검토·적용하고 보안/성능 advisors와 anonymous 접근 차단을 확인한다. 기존 과거 마이그레이션 전체를 공유 DB에 다시 실행하지 않는다. `container-member-api` 배포에 `_shared/companyAction.ts`, `_shared/companySnapshot.ts`도 포함하고 기존 `verify_jwt=false` 설정을 유지한다(함수 내부 opaque 인증 필수). DB → Edge API → 웹 순서로 적용하고 두 개의 실제 테스트 계정으로 기업 격리·초대·저장·검토·권한 회수를 확인한다.

본 브랜치에서 운영 DB/Edge 변경과 main 병합은 하지 않았다. GitHub PR의 웹 미리보기가 생성되더라도 새 DB·Edge가 준비되지 않은 서버는 명확한 오류를 표시하며 로컬 저장이나 가짜 성공으로 대체하지 않는다. 서비스 출시 전 이메일 소유 확인, 독립 DB 세션 경합, 서버 재검증 증거, 백업 복구 등 운영 검증은 별도로 필요하다.
