# 적재 대기장 렌더링 측정 기록

이 문서는 화면 준비·자원·렌더링 비용의 측정 조건과 결과를 기록한다.
적재 엔진 처리량, 물리 검증 결과나 운송 안전 인증을 뜻하지 않는다.
단위 테스트의 자원 해제 확인과 브라우저의 실제 GPU 실행 결과도 구분한다.

## 확인한 실행 환경

2026-11-17 로컬 작업 환경에서 읽기 전용으로 확인했다.

| 항목 | 확인값 |
| --- | --- |
| 운영체제 | Windows 11 Pro, 10.0.26300 |
| CPU | Intel Core i7-13700, 16코어 / 24 논리 프로세서 |
| 설치된 그래픽 장치 | NVIDIA GeForce RTX 4060 |
| Node.js | 26.13.0 |
| Three.js | 0.185.1 |
| React / R3F | 19.2.8 / 9.7.0 |
| Playwright | 1.60.0 |
| 대기장 E2E 프로젝트 | `chromium-desktop` |
| 대기장 E2E viewport | 1366×768, 1920×1080 |
| 대기장 E2E 그래픽 옵션 | `--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist` |

설치된 GPU와 브라우저가 실제 선택한 렌더러는 별개다. 위 대기장 E2E는
SwiftShader 경로를 요청하므로 그 결과를 RTX 4060 하드웨어 GPU 성능으로 기록하지 않는다.
하드웨어 측정은 브라우저의 실제 WebGL vendor/renderer, DPR, 브라우저 버전과
headed/headless 여부를 별도로 기록한 실행만 사용한다.

## 재현과 비교 조건

- 동일한 화물 입력·실제 포장·채택된 차량 배치를 사용한다. 품질 설정을 비교하며
  재적재하거나 물리 검증을 다시 실행하지 않는다.
- 전체 실제 화물 수와 화면에 표시한 화물 수를 함께 기록한다. 대형 작업은 구역
  페이지 때문에 일부 화물만 렌더링하므로 전체 수량을 렌더링 개수로 보고하지 않는다.
- 화면 크기와 실제 DPR, 카메라·구역, 품질 단계와 AO 사용 여부를 고정한다.
- 최초 모델 요청부터 준비 완료까지와 캐시가 준비된 후의 장면 생성 시간을 나눈다.
  JS 초기 로딩·네트워크·텍스처 디코드 시간을 제외한 수치는 제외 사실을 적는다.
- 렌더 회전 벤치마크의 표본 수, 실제 지속 시간, 평균·p95 프레임 시간과 FPS,
  draw call·삼각형 수를 함께 기록한다. 비활성 demand 화면의 대기 시간을 FPS로 환산하지 않는다.
- 픽셀 비교는 품질 설정·동일 카메라·같은 렌더러 안에서 수행한다. AO 켜짐/꺼짐에서
  투명 랩·라벨·선택 강조의 경계와 원래 품목색을 함께 확인한다.
- 품질 반복 변경, viewport/DPR 변경, 구역 왕복, 장면 재생성 후 안정된 자원 수를
  비교한다. 공유 모델 캐시의 유지와 장면 전용 render target 누수는 구분한다.

## 최종 장면의 소프트웨어 렌더링 관측

2026-11-17 14:58 KST 로컬 작업 트리에서 clean kraft 박스 재질·얇은 랩 필름·현재
카메라 소스를 사용한 실행이다. 기본 ANGLE 경로를 요청했지만 **실제 렌더러는
SwiftShader Device (Subzero)**였다. 하드웨어 GPU 실측이 아니다. 실행 파일명에
`hardware`가 들어간 것은 요청한 시도의 이름이었으며 실제 장치를 뜻하지 않는다.

- 브라우저: Chromium / Chrome 148.0.7778.96, Windows, WebGL 2.0.
- 실제 renderer: `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)`.
- viewport 1920×1080, DPR 1, 실제 beauty 출력 1448×484 픽셀.
- 같은 16박스·2파렛트 장면과 같은 초기 카메라. 모든 표본의 pose는
  `5.52436,5.24666,6.13543,-0.21794,0.34847,0.08366,0.90779`로 같았다.
- 로드된 동일 장면에서 품질별 5초 회전 1회씩 측정했다. 최초 네트워크·모델 준비 시간을
  재는 실험이 아니며, 반복 시행의 분산이나 기기 간 결과를 대표하지 않는다.

| 품질 | 출력 경로 | 표본 수 | 지속 ms | 평균 프레임 ms | p95 ms | FPS | AO 버퍼 px | 실제 후처리 MSAA | calls/frame | triangles/frame |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 성능 우선 | 직접 | 163 | 5014.20 | 30.76 | 35.70 | 32.51 | 없음 | 0 | 54 | 24,482 |
| 표준 | GTAO | 70 | 5004.60 | 71.49 | 80.90 | 13.99 | 724×242 | 0 | 107 | 47,767 |
| 고품질 | GTAO | 18 | 5140.50 | 285.58 | 341.10 | 3.50 | 1448×484 | 4 | 107 | 47,767 |

표는 읽기 쉽게 소수 둘째 자리로 반올림했다. 표본·지속 시간·실제 버퍼 크기와 반올림
전 값은 [원본 관측 JSON](staging-yard-quality-2026-11-17.json)에 보존한다.
호출·삼각형 수는 장면·그림자·후처리를 포함한 프레임 제출 집계이며 고유 geometry
개수나 실제 화물 개수와 다르다. 표준은 MSAA 2를 요청했지만 이 실행의 RGBA16F
지원 표본 수가 4만 허용해 상한 안의 조합이 없어 실제 0을 사용했다.

이 소프트웨어 환경에서는 고품질이 표준보다 느렸다. 고품질의 더 큰 AO 버퍼·표본·
그림자·MSAA 비용이 있는 측정이며, 다른 GPU에서의 FPS를 보장하거나 중간 버전 대비
개선율을 계산하지 않는다. 품질 전환 3회 후 집계는 모두 geometry 12 / texture 8로
같았다. 이 유한한 반복 관측은 VRAM 바이트 측정이나 장기 누수 보증이 아니다.

QA 원본 추출 파일은 저장소 옆 `../staging-yard-qa/angle-default-quality-measurements.json`
이며, 위 저장소 내 JSON은 같은 내용의 복사본이다. 참고 사이트 화면이나 과거 baseline
이미지를 이 측정의 구현 결과로 사용하지 않는다.

## CPU 준비 측정의 범위

`src/stagingYardPerformance.test.ts`는 한 SKU에 5,000개·10,000개를 요청하고 warmup
1회 후 5회 측정한다. 전체 재고·슬롯·구역은 보존하면서 표시 4구역의 실제 32개만
장면 인스턴스로 준비한다. 재고 도출, 최초 배치, 기존 슬롯을 유지한 재배치, 구역
부분집합 추출과 장면 자원 준비 시간을 나눠 기록한다. 구역 추출은 100회 반복 평균이다.

원본 OBJ 파일 읽기·파싱과 원본 모델 fixture 준비는 타이머 밖에서 수행한다. 이 측정에는
텍스처 요청·디코드, Canvas 라벨, 실제 WebGL 제출과 GPU 프레임 시간이 들어가지 않는다.
geometry·material 참조 수는 CPU 장면 객체에서 센 고유 참조 수이며
실제 GPU 메모리 할당이나 VRAM 크기가 아니다. 전체 요청 개수를 GPU에 동시에 그린
개수로 보고하지 않으며, 이 준비 시간으로 렌더 FPS나 엔진 계산 속도를 추정하지 않는다.

2026-11-17 최종 CPU 측정의 최초 layout 중앙값은 다음과 같다. 각 경우 warmup 1회 후
5회이며, Node 26.13.0 환경의 CPU 준비 시간이다. 브라우저 프레임 측정 표와 다른 실험이다.

| 실제 박스 / 전체 슬롯 | 전체 구역 | 표시 구역 / 박스 | 최초 layout 중앙값 ms | 표시 박스의 삼각형 제출 전 개수 |
| --- | --- | --- | --- | --- |
| 5,000 / 5,000 | 625 | 4 / 32 | 24.184 | 108×32 = 3,456 |
| 10,000 / 10,000 | 1,250 | 4 / 32 | 79.670 | 108×32 = 3,456 |

108은 공유 작업 화면 박스 1개의 표시 형상 삼각형 수다. 위 3,456은 표시 박스만의
인스턴스 합계이며 바닥·라벨·파렛트·차량·그림자·AO 제출을 포함한 실제 프레임 집계가 아니다.

Windows Node 26에서 기존 테스트 환경 옵션을 포함한 재현 명령:

```powershell
$env:NODE_OPTIONS='--no-experimental-webstorage'
npm test -- src/stagingYardPerformance.test.ts --reporter=verbose --silent=false
```

## 브라우저 품질 비교의 범위

`e2e/three-render-quality.spec.ts`는 같은 16박스·2파렛트 장면을 고정된 초기 카메라와
1920×1080 viewport에서 세 품질 및 AO 꺼짐으로 비교한다. 각 품질의 5초 회전 측정을
개별 표본으로 기록하고 실제 WebGL renderer·DPR·AO 버퍼 크기·MSAA와 자원 수를
함께 확인한다. `e2e/staging-yard.spec.ts`는 실제 작업 화면에서 품질 변경이 수량·
결과·식별자·카메라를 바꾸지 않는지, 5,000개 작업도 표시 구역과 실제 드래그를 연결하는지 검사한다.

최종 화면 재질 변경 전이나 카메라가 달랐던 중간 측정은 개선율의 기준으로 사용하지
않는다. 최종 renderer에서 다시 얻은 JSON을 이 문서의 결과 표와 연결해 보관한다.

## 관련 검증

기능 계약과 안전 경계는 [적재 대기장 기능 문서](../features/STAGING_YARD.md)를 따른다.
화면 E2E는 `e2e/staging-yard.spec.ts`, 기존 Three 자원·재질·장면 테스트는
`threeComparisonModels.test.ts`, `threeComparisonScene.test.ts`,
`ThreeVehicleLifecycle.test.tsx`, `threeViewerEnvironmentResources.test.ts`에 있다.
품질 후처리 테스트의 모의 renderer 검증은 실제 WebGL 셰이더 컴파일·화면 비교와 구분한다.
